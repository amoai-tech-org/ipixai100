### 3. Restore a real current cycle

This is the biggest process problem.

Live iPix1 currently returns:

```text
Current cycle: none
```

Linear cycles are meant to be repeating, time-boxed periods with a predefined work set. Linear can automatically create future cycles and even auto-add active work.

You currently have started work tied to:

- an expired cycle
    
- a future Sep 14 cycle
    
- no actual current cycle
    

Fix this before using cycle membership as a planning signal.

Recommended:

```text
2-week recurring cycle
start current cycle now
next cycle automatically follows
```

Do not manually create gaps between cycles unless you intentionally want cooldowns.

This will make cycle capacity and velocity much more meaningful.

### 6. Tighten priority usage

You currently have many `Urgent` and `High` tasks across M1–M4.

Linear priorities are useful only when they discriminate.

Use:

|Priority|iPix meaning|
|---|---|
|Urgent|Active blocker/outage/security/release blocker|
|High|Current milestone critical path|
|Medium|Parallel useful work|
|Low|Cleanup/polish|
|None|Unscheduled backlog|

Specific improvement:

**IPI-1116 · CLD-UPLOAD-001 — Let Operators Upload Shoot Selects with the Cloudinary Widget** is `Urgent` while still Todo and blocked by upstream work. It should probably be **High** until it becomes the actual next critical-path task.

Same principle for future-release items such as **IPI-1091 · RELEASE-001 — Deploy the New iPix App to Vercel and Prove the Complete Production Journey**: Urgent should mean “needs attention now,” not “important eventually.”

### 8. Introduce one standard issue template

Linear templates can preset team, status, priority, project, labels, estimate, assignee and even sub-issues.

Create one team template:

**iPix · Executable Task**

Structure:

```text
Purpose

User outcome

Current state / source of truth

Dependencies
blockedBy:
relatedTo:

Recommended implementation

Faster/better approach

Acceptance criteria

Verification

Risks

Next task
```

Default properties:

```text
Project = v2-ipix
Status = Backlog
Priority = None or Medium
Milestone = required when ready
Estimate = blank until planning
Assignee = blank until committed
```

This prevents every issue from inventing a different structure.

### 9. Use sub-issues only for true decomposition

Your current hierarchy is mostly good:

```text
Epic
→ capability parent
→ executable issue
```

Example:

```text
IPI-1102 Production & Media
→ IPI-1097 MEDIA-001
   → IPI-1116 Upload
   → IPI-1118 Attach
   → IPI-1119 Approval
   → IPI-1120 Delivery
```

That is useful.

Do not add another level such as:

```text
Epic
→ capability
→ feature
→ implementation
→ test
```

At that point the hierarchy becomes harder than the work.

Use sub-issues when a child can be independently completed and verified; use checklist items for tiny implementation steps.

---

### 10. Use estimates only on committed executable work

Estimates are currently inconsistent: a few issues have `2/3/5/8`, most have none.

Do not estimate the whole backlog.

If you want useful cycle capacity, estimate only:

```text
current cycle
+ next-ready executable issues
```

Simple scale:

```text
1 = tiny
2 = small
3 = normal
5 = large
8 = must consider splitting
```

If an issue is `8+`, ask whether it should become sub-issues.

For a highly AI-assisted project, estimates are more useful as **relative complexity/risk**, not developer-hours.

---

### 11. Keep due dates rare

Current project issues mostly have no due dates. That is good.

Use due dates only for genuine external commitments:

```text
client deadline
production cutover window
security deadline
launch date
contractual obligation
```

Do not use issue due dates as a substitute for cycles or milestone target dates.

---

### 12. Keep project-level dependencies unused for now

You still have one primary execution project:

```text
iPix V2 Initiative
```

So issue-level relations remain correct.

Use project dependencies only once you actually split into independently managed projects, for example:

```text

```

Until then, `blockedBy` on issues is simpler and more precise.
